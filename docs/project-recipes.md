# 專案配方與商用就緒度

Morning Operator 的專案配方不是新的產業包，也不是收入保證。它們把已稽核專案中可重複的工作模式，映射到既有六種產業包，讓學員能從固定範圍、安全邊界與可驗證的完成條件開始。

## 六種配方

| 配方 | 既有產業包 | 吸收的優點 | 淘汰或阻擋的缺點 |
|---|---|---|---|
| 團購營運 | commerce operations | 低成本表單、試算表協作、後端計價與鎖定 | 匿名個資、公開成本、任意數量、非冪等訂單、未驗證轉帳 |
| 授權 IT 監控 | professional services | 可攜式 CLI、證據報告、明確 B2B 問題 | 未授權掃描、靜態快照冒充監控、未驗證二進位、缺少 CI |
| SEO 基礎改善衝刺 | professional services | 一個授權網域、一種語言、最多 20 URL、三頁 brief、可審閱 patch 與 90 天量測 | 排名保證、關鍵字堆砌、買連結、假評論、入口頁、未核准發布與個資進 AI |
| 製造異常看板 | back office | 瀏覽器端匯入、清楚分析介面、唯讀導入 | 無界限檔案、硬編門檻、無持久化／整合、行動版溢出 |
| 社群活動櫃台 | appointments | 佇列、核准、稽核、重試、死信與測試 | 無驗證身分、Mock 冒充外送、缺少正式部署與 CI |
| 私人家計紀錄 | back office | OAuth、加密、去重與低成本私有執行 | 跨家庭資料、偽造身分 header、半套交易、公開部署與自動財務決策 |

每個配方都宣告版本、輸入、輸出、免費優先部署選項、覆蓋範圍、衡量指標、必要核准、禁止動作、隱私與金流邊界、設定步驟、驗證清單、已知限制及收益情境聲明。配方 registry 位於 `src/lib/project-recipes.ts`，新增或修改配方必須通過 registry 測試與人工審查。

## 使用專案啟動台

1. 在公開頁選擇最接近的配方。
2. 只填寫目前已能提出證據的狀態；不貼客戶、訂單、家庭、參與者或機密紀錄。
3. 執行就緒度檢查，先處理 P0，再處理 P1 與 P2。
4. 使用「帶入免費健檢」把 recipe ID、產業包與主要目標預填到既有 intake；手動改變 pack 或 goal 會清除 recipe 綁定。
5. 正式送出後仍依序經過付款驗證、規格核准、隔離建置、QA、部署核准與交付；啟動台不會縮短這條核准鏈。

`POST /api/project-readiness` 是無持久化預覽 API。它只接受配方 ID 與非個人化的證據枚舉，回應使用 `Cache-Control: no-store`，不建立 lead、payment、project、job 或 approval。

正式 intake 會把經驗證的 recipe ID 與版本寫入 lead；規格草稿會再次核對 recipe、pack、goal 及版本，並把該 recipe 的固定輸入、輸出、衡量指標、必要核准、禁止動作與驗收檢查納入規格。SEO 詳細邊界見 [SEO 主力服務](seo-service.md)。

## 四個分數不能混為一談

- 作業執行率：功能、展示、持久化、測試、部署及文件是否能被驗證。
- 商用交付率：身分、資料隔離、冪等、金流簽章、重試／死信、測試及營運證據是否足夠。
- 商機情境：問題強度、買方清晰度、需求、定價與付費證據的情境分數。
- 變現就緒度：商用交付與市場證據的綜合情境；不是預測營收。

跨租戶或匿名個資、未驗簽真實金流、Mock 冒充真實結果，以及有副作用卻缺少冪等，都是 P0 商用阻擋。再漂亮的畫面、CI 或公開 Demo 都不能抵銷這些問題。

## 驗證

```powershell
pnpm vitest run tests/project-recipes.test.ts tests/project-readiness.test.ts tests/project-readiness-api.test.ts
pnpm verify
pnpm test:e2e
```

所有覆蓋率、商機、變現與收入文字都只是範圍或情境，不保證收入、節省、需求或成功。
